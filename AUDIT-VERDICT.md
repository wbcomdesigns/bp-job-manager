# Audit Verdict: bp-job-manager

**Branch:** 2.8.5 (QA dark-mode round 2 just pushed) · **Audit type:** STATIC ONLY, read-only · **Date:** 2026-07-03

## Shippable? NO — WITH FIXES
Blocked by one confirmed data-disclosure defect (#1) and one confirmed release-integrity defect (#2) that undermines the very dark-mode fix this branch exists to ship. Both are small, isolated, one-file fixes — not a rewrite.

## Sellable? WITH POLISH
Architecture is sound (hook-driven wrapper around WPJM/BuddyPress, no REST attack surface, settings wired end-to-end admin→global→frontend). Once #1–#3 are fixed and the RTL/i18n/breakpoint debt is swept, this clears a premium bar.

| 1 | **Blocker** | Security | `bpjm_load_more_jobs` nopriv AJAX handler filters jobs by `'author' => bp_displayed_user_id()`. WP core (`class-wp-query.php` line 983: `if ( empty( $query_vars['author'] ) \|\| '0' == $query_vars['author'] )`) **drops the author filter entirely** when the value is `0`/empty. `bp_displayed_user_id()` returns `0` whenever BuddyPress hasn't parsed a member-profile URL into `$bp->displayed_user` — which is the normal case for a raw POST to `admin-ajax.php` (no `/members/{user}/` path to parse). Net effect: the handler falls back to `get_posts()` with **no author filter and `post_status` = publish/expired/pending/draft/preview**, returning every user's job listings — including unpublished/draft/pending ones — to any anonymous caller who has the (page-embedded, non-secret) nonce. | `public/class-bp-job-manager-public.php:204-226` (handler); registered `public/class-bp-job-manager-public.php:70-71`; JS caller `public/js/bp-job-manager-public.js:76` | `/bug-fix` → pass the displayed-profile user ID explicitly in the AJAX payload (JS already knows the profile it's on) and re-validate it server-side against `bp_displayed_user_id()`/a signed value; reject with `wp_send_json_error()` if `author` resolves to 0 instead of silently querying all authors. |

### Additional lower-severity notes (Polish, not release-blocking)

- **i18n gap**: `"Loading..."` button label is hardcoded directly in JS markup, not passed through `wp_localize_script`'s i18n object, so it never translates. `public/js/bp-job-manager-public.js:~80` (`beforeSend` handler).
- **Debug leftover**: `console.log("asd")` in the click handler for the job-application button. `public/js/bp-job-manager-public.js:7`.
- **RTL gaps**: raw `margin-left`/`padding-left`/`padding-right`/`margin-right` (physical, not logical properties) in the public stylesheet and admin.css — `public/css/bp-job-manager-public.css:32,92,105,317`; `assets/css/admin.css:286,529,1033`.
- **Breakpoint sprawl**: 6 distinct `@media` breakpoint values across the CSS (canonical target is ≤3).
- **Raw hex outside `:root`**: ~20 hex literals in the dark-mode block of `public/css/bp-job-manager-public.css` (lines 79-618) — largely the intentional bridged dark palette from the 2026-06-30/07-03 QA fixes per CLAUDE.md, but not tokenized per `ux-foundation` convention; low risk, worth a follow-up token pass.
- **WPCS**: 455 errors / 109 warnings across 32 files, dominated by PEAR formatting and inline-comment punctuation (503 auto-fixable via `phpcbf`) plus several `WordPress.DB.DirectDatabaseQuery.NoCaching` warnings in `class-bp-job-manager-function.php` (ties to finding #4). This is pre-existing debt, not introduced by the CSS-only dark-mode patch on this branch.
- **Contract audit** (`wp-contract-audit` script, static, 0 errors / 1 warning): only flagged finding is `bpjm_load_more_jobs` as an "unreferenced AJAX handler" — **verified false positive**, the action is called from `public/js/bp-job-manager-public.js:76` (the contract scanner's scope apparently excludes `public/js/`). No orphaned CSS selectors targeting non-existent markup, no consumed-never-fired hooks, and no dual-meta-key drift were found — the recent dark-mode CSS additions target real, existing WPJM/BP markup.
- **Three-entry-points**: the plugin's one setting, `bpjm_general_settings`, is written only via the admin settings form (`includes/admin/views/settings-general.php`) and is read + enforced end-to-end (`includes/class-bp-job-manager-globals.php:133` → frontend role-gating in `bpjm_member_profile_jobs_tab()`). No REST surface exists for this plugin by design (manifest: 0 REST endpoints, hook-driven-only architecture) — not a gap.

## Summary for the release gate

This branch's actual deliverable — the dark-mode CSS fixes — is contract-sound and low-risk. But two unrelated, pre-existing bugs sit directly in its blast radius: the cache-busting bug (#2) means the CSS fix itself may not reliably reach users, and the AJAX author-filter bug (#1) is an active data leak independent of dark mode. Recommend fixing #1 and #2 in the same release (both are 1-line-scope changes), track #3/#4 as fast-follow performance work, and sweep #5 + the Polish list on the next UX pass.
